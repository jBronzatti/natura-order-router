● Yes, some recommendations change. Your framing also showed me a whole set of
  input types I hadn't covered. I rewrote docs/decisions.md so every decision is
  now a rule for a type of input, built into the code, instead of a fix for one
  order. I also updated docs/analysis.md and docs/test-plan.md to match, and I
  didn't touch the JSON files.

  Recommendations that changed

  - ZIP handling (D-01 and D-07 are now one decision). My old D-07 advice was
    "just take the first 3 characters." Now I recommend a strict ZIP check for
    every type of value:
    - A number gets its leading zeros added back, because that's the only way a
      number loses digits.
    - A short string like "2134" is rejected as an invalid ZIP. Any digit could
      be missing, so padding it can point to the wrong region: "3030" would
      become New Hampshire instead of Atlanta.
  - SKU normalization (D-03) now applies the same way everywhere: order lines,
    edits, the catalog and warehouse inventory. If two SKUs become the same
    after normalizing, that's a configuration error.
  - Missing country (D-06) gets its own reason, NO_COUNTRY, instead of being
    counted as international.

  New decisions

  - D-00, the main rule. There are two levels of trust:
    - Order events come from customers, so they never crash the run. An order
      that can't be routed safely goes to PARTNER with a clear reason code, plus
      a warning.
    - Warehouses, zones and the catalog are our own configuration. They're fully
      checked at load time, and the run stops with a clear error if something
      is wrong. Bad configuration would misroute every order without anyone
      noticing.
  - D-18: invalid order lines: a bad quantity (0, negative, decimal, "2") or a
    missing SKU. I recommend sending the whole order to PARTNER rather than
    dropping the bad line. Dropping it would ship an order the customer never
    placed.
  - D-19: a missing order number, or the same order created twice.
  - D-20: unknown event types.
  - D-21: a warehouse that isn't in the rule-6 priority list.
  - D-22: the full checklist for validating the configuration files.
  - D-13 and D-14 got new cases: an unreadable timestamp, an edit dated before
    its order, and an edit with an invalid line.

  Trade-offs you need to pick

  Your coding rules say to ask when the simple option and the robust one really
  differ. These three are like that:
  - D-02: a bundle that contains another bundle. Simple: reject it when the
    catalog loads. Robust: expand it recursively and detect loops.
  - D-06: country aliases. Simple: accept only US. Robust: also accept names
    like USA or United States.
  - D-21: a warehouse missing from the priority list. Lenient: put it at the
    end. Strict: treat it as a configuration error.

  The test plan has two new sections. Section 10 checks that bad order data
  never crashes the run. Section 11 checks that bad configuration stops the run
  at load time. The ZIP tests are now one table with a row per type of input.
